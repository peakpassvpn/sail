# sail's C ABI for apps

`sail-ffi` builds `libsail` (static and dynamic) with the C interface
declared in [`sail-ffi/include/sail.h`](../sail-ffi/include/sail.h). The
header's comments are the reference for each function; this page is the
contract they share, and what an app does with them.

The header is generated by cbindgen and committed. After changing an
exported function or constant, generate it again in `sail-ffi/`:

```
cbindgen --config cbindgen.toml src/lib.rs -o include/sail.h
```

A test fails when the header no longer declares what the source exports,
and another compiles it as C11 and C++17.

## Instances

```c
SailPlatform platform = { .struct_size = sizeof(SailPlatform), .context = app,
                          .release = app_release, .protect_socket = protect,
                          .open_tun = open_tun };
SailInstance instance;
char *err = NULL;
if (sail_instance_new("{\"data_dir\": \"...\"}", &platform, &instance, &err) != SAIL_OK) { ... }
if (sail_instance_start(instance, config_json, &err) != SAIL_OK) { /* err says why */ }
/* ... */
sail_instance_stop(instance, 5000, NULL);
sail_instance_free(instance);
```

- An instance is made idle, with its settings and the host's callbacks, and
  started from a configuration in any format sail reads (sing-box's JSON,
  Clash's YAML, a Surge profile), or from a file. It runs on a thread of its
  own; `sail_instance_start` returns once it runs, or with why it failed.
- It can be started again after it stopped or failed, reloaded while it
  runs (with a new configuration, or its file again), stopped, and freed.
  Any number of instances run at once, each with its own log.
- A stop while the instance starts ends the start: the start returns
  `SAIL_ERR_CANCELLED`. Stopping an instance not running does nothing.
- `sail_instance_free` asks the instance to stop without waiting, and ends
  its subscriptions. The platform's `release` is called once the instance
  has stopped: from then on, sail calls none of its callbacks.
- Settings: the core's start settings (`profile`, `set`, `data_dir`,
  `cache_dir`, `log_to_system`, `socket_protect`, `sub_store`,
  `ui_download_url`, `asset_sources`), and the FFI's own: `log_lines`, the
  lines of its log kept (3000, as both sing-box apps keep), and
  `worker_threads` (unset or 0: one thread) with `stack_size`. An unknown
  setting is an error. On iOS and Android the "mobile" profile and the
  system log are the defaults.

## The contract

**Handles.** Instances, subscriptions and delay tests are 64-bit handles; 0
is never one. A handle freed or never given makes a call fail with
`SAIL_ERR_NO_INSTANCE`, never undefined behaviour: a freed handle is not
given again.

**Errors.** Every call returns a `SAIL_*` code. A call taking `char **err`
writes a message there when it fails, which the host frees with
`sail_free_string`, and NULL when it succeeds; NULL for `err` asks for no
message. The codes are stable: `SAIL_ERR_INVALID_ARGUMENT`,
`SAIL_ERR_NO_INSTANCE`, `SAIL_ERR_STATE` (not running, or started already),
`SAIL_ERR_CONFIG`, `SAIL_ERR_IO`, `SAIL_ERR_NOT_FOUND`,
`SAIL_ERR_UNSUPPORTED`, `SAIL_ERR_CANCELLED`, `SAIL_ERR_TIMEOUT`,
`SAIL_ERR_WRONG_THREAD`, `SAIL_ERR_INTERNAL`.

**Memory.** Strings passed in are NUL-terminated UTF-8, read during the
call only. Strings returned are sail's, freed with `sail_free_string`. The
JSON an event callback gets is valid during the call only: copy what is
kept.

**JSON.** Structured data is sail's own JSON: sail's control types
serialized directly, snake_case, typed (ports are numbers, a missing value
is null). It is not the Clash API's shape, which the Clash API renders from
the same types. It is core's (`sail::control::json`), which the
management API answers with too. A snapshot test pins it: a change to it is
a change of the contract, raising its version (`json_version` in
`sail_capabilities`) and `SAIL_API_VERSION`.

**Threads.**

- The platform's `protect_socket` is called on the instance's threads as it
  dials; `open_tun` on the thread starting it. Neither may wait on sail: a
  call that would wait on the instance fails there with
  `SAIL_ERR_WRONG_THREAD` rather than wait on itself, and a stop there asks
  without waiting.
- Every event callback of an instance is called on its events thread, one
  at a time, in order for each subscription, and never while sail holds a
  lock of its own. A host that wants its main thread goes there itself.
- A callback may call any function, for its own instance too: end its own
  or another subscription, stop the instance and wait for it, free it.
- A slow callback delays only its instance's events. The traffic flows on;
  a status or the connections are sent less often; log lines are left out,
  and counted in the next event's `dropped`.

**Cancellation.** `sail_unsubscribe` returns once no callback of the
subscription runs or will run, and its `release` has been called. Called
from a callback on the events thread, it ends the subscription after that
callback returns. A callback must not wait on a lock the thread
unsubscribing holds. `sail_cancel` stops a delay test.

**Release.** Each `context` the host gives (the platform's, each
subscription's) is released exactly once, after the last callback passing
it: the platform's once the instance is freed and has stopped, a
subscription's when it ends or its instance is freed. A callback of the
host's already running when the instance stops (`find_connection_owner`,
say) is not waited for: the stop returns while it may still run, and the
platform's `release` comes after it returns, so a host slow to answer
delays its own release. A call that fails takes nothing: its context is
never released.

**Panics.** A panic inside sail aborts the process in release builds, as a
Go panic in libbox does; in debug builds it is caught and returned as
`SAIL_ERR_INTERNAL`.

**The app's process dying.** Nothing is left that the system does not take
back: sockets, the TUN device and the cache file's lock go with the process,
and the next start with the same directories runs.

## What an app asks and follows

| | Once | Followed (`sail_subscribe`) |
| --- | --- | --- |
| State | `sail_instance_state` | `SAIL_EVENT_STATE` |
| Traffic | `sail_traffic` | `SAIL_EVENT_STATUS` (rates, each interval) |
| Connections | `sail_connections`, `sail_close_connection`, `sail_close_all_connections` | `SAIL_EVENT_CONNECTIONS` |
| Outbounds and groups | `sail_outbounds`, `sail_groups`, `sail_select` | `SAIL_EVENT_OUTBOUNDS` (on change) |
| Delays | `sail_delay` (waits), `sail_url_test` (does not; a group's members), `sail_cancel` | through `SAIL_EVENT_OUTBOUNDS` |
| Providers and rule-sets | `sail_providers`, `sail_update_provider`, `sail_rule_sets`, `sail_update_rule_set` (an update waits for it; no URL is told, as a subscription's carries its token) | |
| Mode | `sail_mode`, `sail_set_mode` (an instance has modes though its configuration has no Clash API, as libbox's apps do) | |
| Log | `sail_clear_logs` | `SAIL_EVENT_LOG` |
| Network | `sail_set_network_state`, `sail_network_changed` | `SAIL_EVENT_NETWORK` (each change the connections do not survive) |
| Capabilities | `sail_capabilities`, `sail_instance_capabilities` | |

Without an instance: `sail_check_config`, `sail_import_share_links`,
`sail_required_assets`, `sail_test_outbounds`.

The data is what the Clash API reads: the traffic, connections, delays and
selections are the instance's, whoever asks. An instance keeps the delays
measured of each outbound (the last ten), with or without a Clash API.

## Android: per-app proxying

**For hosts**: since API and JSON version 2, with no compatibility with
version 1 (version 3 adds the providers and rule-sets). The TUN request no longer carries `include_android_user`;
`SailPlatform` gains `find_connection_owner`; a connection's JSON gains
`uid` and `packages`. Matching rules by app needs Android API 29 or later
(`getConnectionOwnerUid`).

What goes through the VPN by app is the host's VpnService's to apply, as in
sing-box's apps; sail hands it the lists and routes by app:

| | Who |
| --- | --- |
| `include_package` / `exclude_package` of the tun inbound, in `open_tun`'s request | sail passes them |
| `VpnService.Builder.addAllowedApplication` / `addDisallowedApplication` for them, skipping packages not installed, and the app's own package (added in include mode, left out in exclude mode) | the host |
| `include_uid`, `exclude_uid`, their ranges, `include_android_user` | refused when the host opens the tun (`platform: unsupported uid options`, `platform: unsupported android_user option`, as libbox): a VpnService has no way to apply them. `include_android_user` is refused everywhere: sing-box applies it only on a rooted device opening its own tun |
| Who opened a connection is asked off sail's runtime threads | sail: a slow answer holds up no other connection |
| Who opened a connection: `ConnectivityManager.getConnectionOwnerUid` (API 29+), then `PackageManager.getPackagesForUid` | the host, in `find_connection_owner` |
| The rules `package_name`, `package_name_regex`, `user`, `user_id`, in routing and DNS rules, against what the host said; the uid and packages in the connections list | sail |

With `find_connection_owner`, every connection is asked about before it is
routed, as libbox asks on Android. Without it, those rules are errors.
Below API 29 the host cannot tell, and the rules do not match there.

## The command service

An app whose UI runs in another process than its tunnel (iOS and macOS
Network Extensions; Android when its service runs apart) reaches the
instance through sail's command service, as sing-box's apps do through
libbox's command server:

```c
/* In the tunnel process: */
sail_instance_serve(instance, "{\"path\": \"<app group container>/command.sock\"}", &err);
/* In the UI process: */
SailInstance client;
sail_client_connect("{\"path\": \"<app group container>/command.sock\"}", &client, &err);
sail_groups(client, &json, &err);           /* as for an instance */
sail_subscribe(client, SAIL_EVENT_STATUS, NULL, on_event, ctx, release, &sub, &err);
```

- The service runs on the instance's events thread, from
  `sail_instance_serve` until the instance is freed or it is called with
  NULL: while the instance is idle or failed too, so a UI reads the log of
  a start that failed.
- A client handle answers the same functions as an instance handle, with
  the same JSON and the same codes. What only the tunnel process's host
  does fails there with `SAIL_ERR_UNSUPPORTED`: starting, serving, and the
  network (`sail_set_network_state`, `sail_network_changed`), which the
  tunnel process is told, as in libbox. `sail_instance_stop` and
  `sail_instance_reload` (from its file) through a client call the
  platform's `service_stop` and `service_reload`, so the host stops or
  reloads the instance as its system wants it (iOS's Network Extension);
  without them, sail does.
- A client does not reconnect. When the connection is lost, or the service
  closes, its calls fail with `SAIL_ERR_IO`, and each subscription gets
  one `SAIL_EVENT_DISCONNECTED`, `{"error"}`, then its release. The UI
  connects again.
- Transport: a unix socket, `{"path"}`, at most 103 bytes on Darwin and 107
  on Linux, made the user's only (0600). A file there is replaced when no
  service answers at it, refused (`SAIL_ERR_STATE`) when one does. Or
  loopback TCP, `{"port", "secret"}`, for a host without a shared
  directory (tvOS): the secret, 32 characters at least (`sail generate
  secret`), is sent with every call and compared in constant time. A
  client may also be given a connected socket, `{"fd"}`, as a macOS system
  extension passes one over XPC.
- The protocol is gRPC, its calls libbox's (`daemon/started_service.proto`
  and `managed_service.proto` of sing-box 1.14), in
  [`sail-ffi/proto/command.proto`](../sail-ffi/proto/command.proto). Its
  Rust is generated by `cargo run --manifest-path
  tools/command-proto/Cargo.toml` and committed: the generators are never
  built with sail. A build without the `command-server` feature has no
  service: `sail_instance_serve` and `sail_client_connect` fail with
  `SAIL_ERR_UNSUPPORTED`.

## Swift and Kotlin

[`bindings/swift`](../bindings/swift) is a SwiftPM package (`Sail`, iOS 15
and macOS 13, as sing-box's apps), whose manifest is the repository's root
`Package.swift`, so that an app adds it by URL:
`.package(url: "https://github.com/peakpassvpn/sail", from: "<version>")`
and `.product(name: "Sail", package: "sail")`; a release's tag links the
XCFramework the release publishes. And
[`bindings/kotlin`](../bindings/kotlin) a Kotlin library with its JNI glue,
`jni/sail_jni.c` (Android minSdk 24, as SFA). Both give one class for an
instance or a client, `Sail`, whose calls throw the SAIL code and message,
whose answers are decoded into data types, and whose events are streams
(`AsyncThrowingStream`, `Flow`): ending a stream ends its subscription. The
contract above holds through them; two of their own:

- Swift: a stream's `onTermination` runs under the stream's lock, so the
  package unsubscribes from another thread: the release that follows
  finishes the stream, which takes that lock. A host writing its own
  wrapper keeps the same rule: never wait on sail while holding a lock a
  callback takes.
- Kotlin: the JNI glue attaches sail's threads to the JVM the first time
  each calls back and detaches them when they end, and holds the Kotlin
  objects sail calls back as global references, deleted when sail releases
  them.

Their tests run against a real instance on the host: `bindings/swift/test.sh`
(macOS), and `bindings/kotlin/jni/build-host.sh` then `gradle test` (a
desktop JDK). Each builds sail-ffi first.

## Compared with sing-box's libbox

libbox (sing-box 1.14) gives its apps the same capabilities through a
command server and client. sail differs where noted:

- Many instances in a process, each with its own handle, log, events and
  command socket; libbox runs one.
- A stale command socket is replaced only when no service answers at it;
  libbox removes the file whatever is there.
- A command socket's path longer than `sun_path` is an error that names it;
  the socket is made 0600, where libbox leaves it to the umask.
- Loopback TCP needs a strong secret, compared in constant time; libbox
  takes an empty one, and compares with `!=`.
- The protocol is sail's own (`sail.command.v1`), with libbox's calls and
  their meaning, but not wire-compatible with sing-box's.
- A connection opened shows in the connection events at the next interval;
  libbox pushes it at once.
- When the service closes, its streams end with OK, and a client's
  subscription is told once; libbox stops its server, and its client calls
  `Disconnected` once for each stream.
- A call that fails for the instance's state gets that state's code
  (`FailedPrecondition`, `NotFound`, …), with sail's own; libbox answers
  most with `Unknown`.
- No `grpc.health.v1` service: a client probes with `GetVersion`, as
  libbox's does.
- Not served: the system proxy, debug crashes, OOM reports, network
  quality and STUN tests, notifications, and the Tailscale, Taildrop,
  USB/IP, OpenConnect and OpenVPN calls, for protocols sail does not
  have.
- Delay tests: `sail_url_test` returns at once and its results come as
  outbounds events, as libbox's `URLTest` does; `sail_delay` measures one
  outbound and waits.
- The status event gives rates in bytes a second, where libbox gives the
  bytes of each interval.
