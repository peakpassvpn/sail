## sail 0.18.0 (pre-release)

A pre-release: configuration fields, the C ABI and the Swift and Kotlin
APIs may still change before 1.0. sail now tells its host when someone
else changes what a TUN set up (routes, DNS, its address), on macOS and
Windows. A reload can recheck the connections already open against the
new rules.

Documentation: https://peakpassvpn.github.io/sail/

### Breaking changes

- **A new event kind reaches hosts that subscribe to everything.**
  `Kinds::ALL` (embed) and a C subscription to every kind now also
  deliver `SystemChanged` / `SAIL_EVENT_SYSTEM` (14). `embed::Event` is
  `#[non_exhaustive]`, so Rust matches already had a `_` arm. A C,
  Swift or Kotlin host should ignore kinds it does not know.
- **macOS: a route that auto_route replaced goes back when sail stops.**
  An example is another VPN's 128.0.0.0/1. In 0.17.0 such a route
  stayed gone. It is now recorded when it is replaced, and put back when
  sail's own route goes, at a stop or a rule-set refill. It is put back
  only if sail's route is still there and the interface is still up. A
  route that cannot go back is listed in `StopReport::left`, with the
  command that restores it. After `kill -9`, the next start in the same
  boot puts it back (the ledger).
- **`log.redact` applies to each instance on its own.** Before, it was
  the setting of whichever instance started or reloaded last, so in a
  process with several instances one could log the destinations of
  another in full. A line that belongs to no instance follows the last
  configuration's setting. The NAT64 prefix stays process-wide, and
  docs/embed.md says so.

### TUN

- **Changes made by others are told, never undone.** sail checks its
  TUN setup on each network notice, once the system has been quiet for a
  moment. A route of sail's that is gone, or that another route beats
  for an address it covers, is told. So are a TUN that lost its address
  or went down, and, on Windows only, adapter DNS servers that are no
  longer sail's. Each one is sent as `Event::SystemChanged {kind,
  resource}` (`kind` is `route`, `dns` or `tun`), once per break. It is
  sent again only if the check found it right in between. sail restores
  nothing: the host decides whether to restore it or rebuild the
  instance. A start, a rule-set refill and a stop are never told. Linux
  is out of scope (the host's own guard covers it).
  - macOS: the routes into the utun and its address.
  - Windows: the routes with their next hop, whether 0/0 still wins
    (GetBestRoute2), the adapter's state and address, and its DNS
    servers. DNS changes are watched in the adapter's registry keys,
    because IP Helper gives no notice for them.
  - C ABI `SAIL_EVENT_SYSTEM` `{"kind","resource"}`; Swift and Kotlin
    `systemChanges()`. A command-service client is refused this kind, as
    it is refused faults.
- A rule-set refill now records only the prefixes it actually added. A
  failed add is retried on the next refill. Before, it was deleted at
  stop although never there, and would have looked like a route someone
  else removed.

### Reload

- **Recheck the connections open.** A reload can be asked to recheck
  them: Rust `reload_rechecking(…, ReloadOptions)`, C
  `sail_instance_reload_with`, Swift and Kotlin `reloadReport(…,
  recheckOpen)`.
  - With `close_rejected`, each connection is matched against the new
    rules once the reload has taken. Those the rules now reject or drop
    are closed. Those that would now go to another outbound are listed
    in `ReloadReport.recheck.differ` and keep running.
  - The default, `keep`, is the reload as before.
  - The recheck reads nothing from the connection and asks no DNS: it
    uses what was sniffed and resolved when the connection was first
    routed.
- An inbounds-only reload frees the ports it gives up: the next reload
  can bind them (test).

### Embedding

- docs/embed.md: several instances on glibc. One hundred instances took
  RSS from 64 MB to 264 MB (133 MB on the host's runtime) while the
  live heap returned to its base. Measured: `MALLOC_ARENA_MAX=2` brings
  this to 92 MB / 79 MB. `malloc_trim(0)` gave back less than a tenth.
- A test starts and stops 100 instances, then 10 rounds of 10 at once,
  first on sail's runtimes and then on the host's. Afterwards nothing is
  left behind: no task, file, thread or runtime, and the heap is within a
  few KiB.

### WireGuard

- A rebind on a port that is not configured takes another port if the
  old one was taken in the meantime. Peers learn the new port from the
  first datagram. On a configured port it is an error. (A test fix,
  plus a log at info.)

### Builds and tooling

- **Mobile libraries link with thin LTO in one codegen unit**
  (`dist-mobile`). Measured on Android arm64:
  - the LTO and link step: 282 s → 185 s;
  - peak build RSS: 8.3 → 6.0 GB;
  - stripped `libsail_jni.so`: 28.7 → 26.9 MB;
  - throughput and CPU per GiB: unchanged.

  TODO (filled after the release run): `SailC.xcframework.zip`, 0.17.0
  → 0.18.0.
- The release workflow builds each macOS target's `sail` and its library
  as separate jobs. The release took 60 min, and now about 46 min.

### Swift and Android

The Swift package needs SystemConfiguration (declared in its module map).

```swift
.package(url: "https://github.com/peakpassvpn/sail", exact: "0.18.0")
```

```kotlin
dependencies {
    implementation(files("libs/sail-0.18.0.aar"))
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.10.2")
    implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.9.0")
}
```
