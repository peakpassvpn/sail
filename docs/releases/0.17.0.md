## sail 0.17.0 (pre-release)

A pre-release: configuration fields, the C ABI and the Swift and Kotlin
APIs may still change before 1.0. sail can now be embedded in a Rust
program, ships builds for routers, and closes two ways a downloaded
profile could write or read files outside the data directory.

Documentation: https://peakpassvpn.github.io/sail/

### Breaking changes

- **Profiles name files only in the data directory** (security, below):
  a Clash profile's `external-ui` outside the data directory, a Clash
  provider or rule-provider `path` on Windows with only a drive or only a
  root (`C:x`, `\x`), and a Surge profile read from text or a URL whose
  `RULE-SET`, `DOMAIN-SET` or `policy-path` names a file outside the data
  directory are now configuration errors. A Surge profile read from its
  own file still names files anywhere, as the operator's own.
- **No version numbers in the interfaces**: `SAIL_API_VERSION`, the
  control JSON's `json_version` and the management API's `api_version`
  are gone; capabilities give the sail release and its compiled-in
  features. `/api/v1` only grows (a break would be `/api/v2`), the C ABI
  is append-only (a change is a new function), and the JSON follows the
  sail release, its breaks listed here. The command client warns, never
  refuses, when the service is another release.
- **A reload applies inbounds** (SIGHUP, `--auto-reload`, the API, an
  embedding host): added, removed and changed inbounds are applied instead
  of the whole reload being refused. The configuration is what runs: an
  inbound removed from it stops and its connections are closed; one
  changed beyond its users and certificate is replaced and its
  connections are closed; an inbound added through the API or
  `add_inbound` and not written to the configuration is removed by the
  next reload. Changes to a TUN inbound still need a restart, and are
  refused with their own error. Embedding hosts: `Instance::reload` now
  returns a `ReloadReport`.
- **New default limits on connections**, which refuse or close what
  0.16.0 accepted, with no change to the configuration (sail extensions;
  neither sing-box nor Mihomo has them):
  - `inbound.max_connections`, the proxied sessions living at once: 512
    with the router profile, no limit otherwise. One more waits a
    second, then is refused (SOCKS reply 1).
  - `inbound.max_handshakes`, connections still in their handshake: 4096
    on a server, 256 on a router, 1024 otherwise; one more is closed at
    once. `inbound.max_handshakes_per_source`, off by default.
  - A server's inbound handshake has 15 s (was 60), as sing-box gives
    TLS and REALITY; a QUIC handshake 5 s on every profile.
- **`local` DNS with no interface**: under a TUN that takes the default
  route, a `local` server whose dialer has no interface to send through
  now fails the query at once (SERVFAIL), where before it handed it to
  the system's resolver, whose query went into the TUN and looped.
- **TUN names**: with no `interface_name`, macOS takes the next free
  `utunN`, as sing-box does, instead of `utun233`. A configured name
  already taken fails the start, as in sing-box.
- **Four new error codes in the C ABI**: a call that failed for one of
  these reasons now returns its own code instead of the one it returned
  before: `SAIL_ERR_PANICKED` (12, was `SAIL_ERR_INTERNAL`: an essential
  task panicked and the instance failed; only in builds with
  `panic = "unwind"`), `SAIL_ERR_NEEDS_RESTART` (13, was
  `SAIL_ERR_STATE`: a reload changes what only a start sets up),
  `SAIL_ERR_TUN_NAME_TAKEN` (14, was `SAIL_ERR_STATE`),
  `SAIL_ERR_INBOUND_LOST` (15, was `SAIL_ERR_IO`). A host should take a
  code its header does not name as `SAIL_ERR_INTERNAL`. The Swift
  (`SailError`) and Kotlin (`SailException`) bindings name the four.
- **The C ABI off Unix**: `{"path"}` and `{"fd"}` for the command
  service are Unix only; on Windows they are `SAIL_ERR_UNSUPPORTED`, and
  `{"port", "secret"}` is the way.
- **`SAIL_EVENT_NETWORK` tells every change**, in order, rather than the
  latest of several in quick succession.
- **Removing an inbound ends what it accepted over TCP**: connections
  still in their handshake and those carrying multiplexed streams too,
  which before went on after `remove_inbound` (QUIC inbounds already
  ended theirs). `remove_inbound`, and a reload that removes or moves an
  inbound, return once its listener is closed (2 s at most): the address
  refuses connections and can be bound at once.
- **`socket_protect` is a Unix socket's path, on Unix only**: sail hands
  each socket over with its descriptor (`SCM_RIGHTS`, one byte each way),
  as sing-box's `protect_path` does. The protocol that sent the
  descriptor's number as an int32, over a Unix socket or TCP, is gone
  with `SocketProtect::Tcp`. An address as `socket_protect`, or
  `socket_protect` off Unix, is a configuration error; a host in the same
  process uses `Platform::protect_socket`. Sockets are protected as soon
  as they are made, before they bind (they were protected after
  binding).
- **Embedding hosts: an instance takes no signals.** Before, with sail's
  `ctrlc` feature, every instance stopped on Ctrl-C and SIGTERM and
  reloaded on SIGHUP; now only sail-cli's does. `StartOptions` has a new
  field, `signals`.
- **Embedding hosts: `runtime::Host` has a new public field, `events`**:
  a literal of it outside sail needs it, or `..Default::default()`.

### Security

- A Clash profile, often one a subscription supplies, could in 0.15.0
  and 0.16.0 set `external-ui` and `external-ui-url` so that sail
  created and filled a directory anywhere the process may write with the
  files of an archive the profile served, and, through `/upgrade/ui`
  (which the profile's own API secret allows), have an existing
  directory renamed away and replaced. Now a directory outside the data
  directory is refused. Update if you run profiles you do not write.
- A Surge profile from a URL could make sail read any local file as a
  rule-set or policy list; such paths now stay in the data directory.
- On Windows, a provider path with a drive or a root but not both was
  written relative to the process's current drive or directory; now
  refused.
- A Shadowsocks request that fails is read on (until the client closes,
  64 KiB, or the handshake deadline) rather than closed at once, so a
  prober cannot learn the header's length from where it is closed
  (Frolov, Wampler and Wustrow, IMC 2020); sing-box resets at once.
- `THIRD_PARTY_LICENSES.md` now lists every crate sail is built from,
  with its license text, and the licenses of the native code built in
  (BoringSSL, mimalloc); every archive and the AAR carry it.

### Embedding

- `sail::embed`, sail in a Rust program: an `Instance` started from
  sing-box JSON, reloaded in place, queried, dialled through and stopped;
  async on the host's own runtime. The C ABI is built on it, unchanged.
- Events: state, network (a snapshot with a generation, then every
  change in order, or `Lagged`), users, group switches, failed dials
  (each member a group tried, its chain outermost first); every
  connection once routed and dialled (`Kinds::ROUTE`), every DNS query
  answered or failed, with its server, source and answers (`Kinds::DNS`),
  and a task that panicked (`Kinds::FAULT`); the route and DNS events are
  built only while subscribed. Inbounds added and removed at run time;
  configuration checked without an instance; which sail it is (release,
  commit).
- The start goes in an order a host can rely on: the network is settled
  first and `network()` answers from then; the outbounds next, so that a
  host can dial through them while the instance starts (a DNS server in
  the host's own process, which the start's lookups go to).
- What an instance changed in the system is undone when it fails or
  stops, while its host's process lives on: on Linux the routes, ip
  rules, nftables table, fw4 drop-in and resolved DNS; on macOS the
  routes and the TUN's DNS; on Windows strict_route's WFP filters, the
  TUN's DNS, the routes and the Wintun adapter, the filters first (DNS
  settings gone with the adapter count as undone). What could not be
  undone is reported, with the command that clears it by hand (`left`,
  below). Tested in CI on each system, in the test's own process.
  Only with `panic = "unwind"` for a panic (Known limits).
- An instance can run on the host's own tokio runtime
  (`Options::runtime(Runtime::Host(handle))`, multi-thread with I/O and
  timers; anything else is refused with `InvalidArgument`): a stop ends
  its tasks within `stop_within` and shuts nothing of the host's down;
  what its tasks log goes to the instance's own log. QUIC endpoints'
  drivers (Hysteria2, TUIC, QUIC inbounds and outbounds), url tests and
  dials run in the instance's scope too, so a stop ends them wherever
  they were started.
- Events subscribed before a start miss nothing told after it: fault,
  group, dial, route, DNS and network events (the C ABI's network
  callback too). User events are still a run's.
- The Clash API's connections and a dashboard's streams (`/traffic`,
  `/memory`, `/logs`, `/connections`) end when the instance stops,
  rather than go on on an embedding host's runtime.
- The C ABI and the bindings tell how a run ended:
  `sail_instance_stop_report`, `error_kind` and `left` (what could not be
  undone) in `sail_instance_state`, and `stopReport()` in Swift and
  Kotlin.
- An instance's tasks belong to it: a panic in one ends that task, is
  logged and told, and the instance goes on (a panic in one it cannot do
  without fails it); a stop ends them all within a bound.
- A TUN's name is settled at start and given to the host; what a killed
  instance left (Linux rules, routes, nftables, the fw4 drop-in) is swept
  at the next start. On Windows a killed instance's Wintun adapter, its
  routes and DNS are gone with it (measured). On Linux, the TUN's DNS
  goes through systemd-resolved only when sail runs in resolved's own
  network namespace, so that a container sharing the host's system bus
  no longer sets the DNS of the host's link of the same index.

### TUN

- On macOS a TUN with auto_route is the system's DNS while it runs, as
  on Linux (systemd-resolved) and Windows (the adapter): the address
  after the TUN's becomes the first resolver. It is a temporary
  dynamic-store key of no real service, so no service's own DNS is
  touched, and it is gone with the process, even after `kill -9`. It is
  undone at a stop, and set again if configd restarts. Nothing is set
  when the host opens the TUN.
- The TCP stack under a TUN and WireGuard waits when its queue is full
  instead of resetting connections that read under load, and an ACK to a
  peer whose window is shut goes at the window's edge, not past it, where
  the peer dropped it and both ends waited on each other for good.

### Inbounds

- `protect_path` (sing-box's) on outbounds and endpoints, DNS servers,
  HTTP clients (rule-sets' too), the REALITY and ShadowTLS handshakes and
  the direct route action; with the host's protection, both apply. A
  configuration error off Unix.
- A SOCKS5 or SOCKS4 refusal, and an HTTP 400 or 407, close with a FIN
  after the reply rather than a reset that could discard it before the
  client read it (Windows most of all).

### DNS

- A `local` server under a TUN that takes the default route asks the
  system's servers itself, through the dialer that is bound to the
  physical interface, rather than through the system resolver, whose
  queries looped into the TUN: on Linux, macOS (the servers of the
  interface it sends through, those set by hand first) and Windows (the
  default adapter's). In order, each with a share of the query's time;
  link-local servers kept on their interface; servers on sail's own TUNs
  left out; failing at once with no interface; read again after a network
  change, and a second after finding none. Where this differs from
  sing-box is in the compatibility notes.
- An answer cut short over UDP (TC) is asked for again over TCP.

### Routing, groups and mux

- A fallback group tests its members at several URLs (any or all),
  moves on from a silent member after `dial_timeout`, and holds back the
  switches a flapping member causes.
- A reload keeps what urltest, fallback and load-balance groups know of
  their members: a member configured as it was keeps its last checks, so
  a rebuilt group chooses at once as after a round of tests, rather than
  taking its first member or one found down until its tests run again.
- sing-mux: `max_connections` alone spreads streams as sing-mux does.
- A local provider's file read while it was being rewritten is read
  again at the provider's interval, not five minutes later.
- A certificate file replaced is served at once, as sing-box does; one
  replaced while the instance starts (an ACME client around a restart)
  is read again once its watch is set up, and so are the configuration
  file and a local rule-set's file.

### Performance

- Linux musl builds (x86_64, aarch64, i686, armv7, arm) allocate with
  mimalloc instead of musl's: a mux upload 1336 → 2248 Mbit/s in an A/B
  of the same build; sail-to-sail against sing-box from 0.88x to 1.10x
  (geometric mean of 16 cells). MIPS keeps musl's allocator, and so do
  the router builds (below).
- QUIC (Hysteria2, TUIC) with sail's quinn fork: BBR's window is bounded
  in Startup, and an old minimum RTT expires; with reordering at 150 ms
  and 50 Mbit/s, what sail sends rose from 2–3 to 20–41 Mbit/s.
- A relayed connection keeps only what relaying needs (an idle direct
  connection about 18.5 KiB of heap), and an idle TLS connection frees
  its handshake configuration once the handshake is done: per idle
  trojan connection, 16.6 → 14.8 KB of heap on a client and 12.6 → 11.4
  KB on a server; throughput unchanged.
- The sail command gives a load's memory back to the system with
  mimalloc too, after a start, each reload and a provider's or
  rule-set's update: at rest after a 3,000-line Clash profile 44.9 →
  27.2 MiB, after 30,000 lines 167.0 → 36.4 MiB (x86_64 musl, router
  profile); throughput unchanged. An embedding host registers its own
  (`sail::runtime::memory::on_memory_freed`; glibc: `malloc_trim(0)`).
- A large profile takes less memory to load:
  - a rule is 864 bytes in memory instead of 1,616 (lists empty in a
    rule allocate nothing);
  - the router takes the rules and drops each once built, rather than
    holding them all beside it;
  - a Clash or Surge profile's adjacent one-domain lines with the same
    target (`DOMAIN`, `DOMAIN-SUFFIX`, `DOMAIN-KEYWORD`) are merged into
    one rule before it is read, and its converted parts are moved, not
    copied. Every line is still reported as itself, by its own index, in
    `Event::Routed`, the log and the Clash API. A native sing-box
    configuration is never merged.

  Peak resident memory (MiB) with 30,000 rules, x86_64 router build:

  | Profile | Start | After a reload |
  |---|---|---|
  | sing-box | 90.4 → 57.4 | 120.4 → 83.7 |
  | Clash | 66.9 → 36.6 | 83.8 → 54.4 |
- Release (dist) builds compile BoringSSL at -O3 instead of -O2: TLS
  handshakes cost about 3% less CPU on x86_64 (measured: 450 → 434 µs
  per client connection, 305 → 296 µs per server connection). Bulk
  encryption throughput is unchanged, its paths being assembly. The gain
  on aarch64 and armv7 is unmeasured and may be larger. Router
  (dist-router) builds keep BoringSSL size-optimised (-Os).
- Sizes, 0.16.0 → this release (the stripped binary, and its archive),
  mimalloc and every other change together, not mimalloc alone; measured
  from the release dry run of 2026-10-03 against the 0.16.0 files:

  | Target | Binary | Archive |
  |---|---|---|
  | x86_64 musl | 22.6 → 23.1 MB (+2.2%) | 9.70 → 9.90 MB |
  | aarch64 musl | 18.5 → 19.0 MB (+2.5%) | 8.84 → 9.04 MB |
  | armv7 hf musl | 18.9 → 19.4 MB (+2.5%) | 9.06 → 9.30 MB |
  | armv7 hf, router build | 11.9 MB | 6.12 MB |
  | mipsel, router build (static) | 16.5 MB | 7.21 MB |

### Windows

- Native builds with MSVC are tested in CI; the release's Windows file
  is still the gnu build. sockets on `::` carry IPv4 too, and QUIC's
  "don't fragment" is the option quinn sets, which made Hysteria2 and
  TUIC to IPv4 servers fail on Windows.
- Building with MSVC needs NASM on PATH (for BoringSSL's assembly).

### Routers

- New `-router` archives: every feature, built smaller (opt-level z, one
  codegen unit: armv7 19.1 MB → about 11 MB), for OpenWrt's packages:
  aarch64, armv7 hard and soft float, arm, x86_64, i686 and mipsel
  (MT7621), mipsel linked statically. Its build is checked for
  reproducibility.
- Router builds allocate with musl's own allocator (mallocng), not
  mimalloc: it holds less memory. x86_64, measured before the load
  changes above: peak resident memory after a 30,000-line Clash profile
  59 MiB against 75 with mimalloc, after a reload 78 against 88; with
  3,000 lines 19 against 35 and 24 against 36.
  The cost is the mux: its upload about half as fast on x86_64. On a
  router's own CPU the trade is unmeasured.

### Builds and tooling

- BoringSSL prebuilt per btls commit and target, as release
  `bssl-<commit>` of peakpassvpn/btls, for projects that build sail from
  source (FORK.md there; sail's own release still builds it).
- `docs/release.md`: how a release is cut and versions are numbered;
  `docs/testing.md`: the four layers CI runs tests in, by what a test
  needs.

### Known limits

- sail-cli and the router packages are built with `panic = "abort"`: a
  panic anywhere in sail ends the process, and the E2 guarantees (a
  task's panic caught, an essential one failing the instance, the
  teardown and its report) hold only in builds with `panic = "unwind"`,
  which the XCFramework and the AAR now are (Changed, below).
  `sail::embed::PANICS_ARE_CAUGHT` tells which a build is.

### Changed

- The XCFramework and the AAR are built with `panic = "unwind"` (profile
  `dist-mobile`). A panic in sail no longer ends the app or the network
  extension: a connection's task's panic ends that task
  (`SAIL_EVENT_FAULT`), an essential task's fails the instance
  (`SAIL_ERR_PANICKED`, its system changes undone), and a panic in a C
  call fails that call with `SAIL_ERR_PANICKED` (it was
  `SAIL_ERR_INTERNAL`). sail-cli and the router packages still abort on
  a panic. The libraries' size changes with it; the release artifacts
  show by how much.

### Swift and Android

The Swift package needs SystemConfiguration (declared in its module map).

```swift
.package(url: "https://github.com/peakpassvpn/sail", exact: "0.17.0")
```

```kotlin
dependencies {
    implementation(files("libs/sail-0.17.0.aar"))
    implementation("org.jetbrains.kotlinx:kotlinx-coroutines-core:1.10.2")
    implementation("org.jetbrains.kotlinx:kotlinx-serialization-json:1.9.0")
}
```
