## sail 0.23.0 (pre-release)

A minor release on top of 0.22.0. A host that embeds sail can register
inbound and outbound kinds of its own and gets a record of each
connection's bytes, user and end; sail's own TCP connections use BBR on
the client profiles; Hysteria2 and TUIC windows grow with the link,
within the device's memory; the mobile profile runs two worker threads.
Apart from the runtime options renamed below, the C ABI and the Swift and
Kotlin APIs only gain.

**The weak-network figures here are preliminary.** Those measured over
netem (loss, delay, jitter and bottleneck queues, in the BBR, TUIC and
QUIC lines below) come before the full cold re-run of the weak-network
suite, and the next release's notes replace them with its figures.

Documentation: https://peakpassvpn.github.io/sail/

### Breaking changes

- **The runtime options `quic.hysteria2_receive_window`,
  `quic.hysteria2_stream_window` and `quic.hysteria2_send_window` are
  now `quic.receive_window`, `quic.stream_window` and
  `quic.send_window`**, as they apply to TUIC too (below). A host or a
  command line that sets the old names (`--set`, the start settings'
  `set`) is refused at start: set the new ones.

### Embedding

- **Connection records, for hosts that bill by traffic**
  (`Kinds::CONNECTION` in `sail::embed`, `?kinds=connection` on the
  management API's `GET /events`): what each connection sent and
  received, its user, inbound, destination, chain, times and how it
  ended, told when it closes, and for a connection still open at each
  interim pass that finds bytes new since its record before: every
  `Options::record_interval` (`Instance::set_record_interval` changes
  it), and when the host asks (`Instance::report_connections`, `POST
  /connections/report`), as before a graceful stop, whose cut
  connections close as `Closed(Stopped)`. The bytes are those its user,
  inbound and outbound were counted, so a connection's records add up to
  what its user was charged, the bytes written after the last read
  included, and a pass racing the close counts none twice. A slow
  subscriber gets `lagged` and no connection waits for it
  (`Options::connection_records` sets how far behind it may fall). The
  C ABI tells them as `SAIL_EVENT_CONNECTION_RECORD`, Swift and Kotlin
  as `connectionRecords()`. A routed connection's event (`Kinds::ROUTE`)
  names its user too.
- **A host registers inbound and outbound kinds of its own**
  (`Options::inbound_kind`, `Options::outbound_kind`), used in a
  configuration by their `type` as sail's are. A host inbound is handed
  each connection sail's listener accepts, within its limits, and submits
  the sessions the connection carries, any number of them, TCP or UDP,
  each with a user, a destination and typed extensions of the host's.
  Sail routes, counts, limits and lists each session as it does its own
  inbounds' sessions. A host outbound gets the session's user,
  destination, inbound and extensions. It returns a stream or datagrams
  it made, or dials through any outbound of sail's by tag (`Via`): a
  routing table of the host's is an outbound kind, swapped without a
  reload. Users come from `Instance::user`. A panic in a host kind ends
  its connection alone, and its tasks go through `sail::embed::spawn`.
  Rust only for now: no C ABI, and no `tls` or `transport` blocks on a
  host inbound (docs/embed.md, Host kinds).
- **A multiplexed connection gives its place among its inbound's
  handshakes back once its handshake is done.** Before, an AnyTLS or
  sing-mux connection, or a UDP-over-TCP one, held the place for as long
  as it lived, so `inbound.max_handshakes` (1024) also bounded how many
  such connections an inbound kept open at once.
- **sail's `[patch.crates-io]` no longer has `netconfig-rs` and
  `route_manager`:** tun-rs's netlink crates come from their crates.io
  releases again. A workspace that copies the section removes those two
  lines; `tools/embed-patch-check.py` allows them as the host's own
  entries, but they would keep the old revisions.

### Default changes

- **Servers and routers hold back unauthenticated connections under
  memory pressure** (sail#15): with less memory free than
  `inbound.memory_reserve` (20% of what the system or the cgroup gives),
  or more connections in their handshake than an eighth of the open-file
  limit, an accepted connection first closes the handshakes stalled past
  `inbound.handshake_stall` (3 s), oldest first; a source whose recent
  handshakes mostly failed is refused (`inbound.score_sources`), and with
  less than half the reserve free every new connection is refused.
  Hysteria2 and TUIC refuse a new connection before its handshake under
  any pressure, since a QUIC handshake under way cannot be closed.
  Sessions that authenticated are never touched. `GET /admission`,
  `?kinds=admission` on `GET /events`, `Kinds::ADMISSION` and
  `Instance::admission()` tell it. `--set inbound.memory_reserve=0
  inbound.handshake_descriptor_share=0` turns it off.
- **The mobile profile runs two worker threads, not one,** in the CLI,
  the embedding and the C ABI, whose default (`worker_threads` unset or
  0) now follows the profile as the others do. On one thread the TUN path
  stopped at about one CPU: Trojan through TUN ran at 4382 / 4306 Mbit/s
  down / up, against 6098 / 6007 on two and sing-box's 5739 / 5468. A
  byte costs about 30% more CPU than on one thread (2.52 against 1.96 CPU
  seconds a GiB down; sing-box 2.83), the idle process wakes 1.1 times a
  second against 0.65, and its anonymous memory grows by under 1 MB with
  the system allocator. A host that wants one sets `worker_threads` to 1.
- **sail's own TCP connections use BBR on Linux and Android on the
  mobile, desktop and router profiles:** the connections outbounds dial
  and those inbounds accept set their congestion control by the new
  runtime option `relay.tcp_congestion`, `bbr` on those profiles and
  empty, the system's, on the server profile. A server opts in with
  `--set relay.tcp_congestion=bbr`, or for every program on it with
  `net.ipv4.tcp_congestion_control = bbr` (`tcp_bbr` loaded); a client
  goes back to the system's with `--set relay.tcp_congestion=`, and any
  other name the kernel knows can be given. Over netem, uploads on the
  mobile, router and desktop profiles are 19–75 times faster than with
  the system's cubic at 0.5% and 2% loss, 1.8–2.6 at 150 ms and 1.5–1.7
  at 300 ms, and in those loss and delay cells retransmit under 3% of
  what is sent (each cell's median); under 25 ± 10 ms of jitter they are
  2.9–3.8 times faster and retransmit 0.02–0.07%. Through a bottleneck
  at 50 Mbit/s to 1 Gbit/s whose queue holds one round trip (20 ms) or
  less, four uploads at once retransmit 10–12% of what they send, cubic
  0.2–0.5%, and one upload 0.3–1.8%; with a queue of two round trips
  they retransmit 0.1–0.2%, and with four, or a cellular-like 0.5 s
  queue at 60 ms, 0.02–0.05%, under cubic's 0.06–0.19% (preliminary,
  as the figures before them). An upload's CPU
  per GiB is cubic's at 1 Gbit/s and below, and about 1.4 times it on an
  unshaped multi-gigabit link.
  Beside a cubic flow in a shallow queue it takes about 90% of the link,
  as the kernel's own bbr does; that is why a server keeps the system's.
  A system that refuses it (the module not loaded, or an app without
  `CAP_NET_ADMIN`, as on Android, asking for one outside
  `net.ipv4.tcp_allowed_congestion_control`) keeps its own, and the
  connection goes ahead; the log says once which one is used. TCP
  Brutal, where a multiplexed connection negotiates it, still replaces
  it. Other systems choose a socket's congestion control themselves, and
  the option does nothing there.

### Memory and performance

- **TLS downloads cost about a tenth less CPU:** a read from the
  transport takes up to four records, where it took one (a system call
  for every 18 KB); the buffer grows only while reads fill it, and an
  idle connection still keeps none. Trojan through TUN on the mobile
  profile: 3917 → 4412 Mbit/s, 2.19 → 1.94 CPU seconds a GiB.
- **TLS uploads cost a tenth to a quarter less CPU:** a write seals up to
  four records and hands them to the transport in one system call, where
  it made one a record. Trojan through TUN on the mobile profile: 3839 →
  4310 Mbit/s, 2.23 → 2.00 CPU seconds a GiB; over SOCKS on the server
  profile 0.61 → 0.47 at the same rate.
- **The TUN stack takes less CPU per packet:** its checksum adds four
  bytes at a time in a loop the compiler vectorizes (2 to 2.5 times the
  speed), each step reads the memory pressure without the rest of the
  budget's counters, and the runtime's flow maps use the stack's fast
  hash. Through a Trojan TUN on the mobile profile with two workers, CPU
  per GiB fell 2.7% uploading and 1.4% downloading, kernel included.
- **An ACK no longer moves a TCP timer in the stack's timer wheel:** a
  retransmission or keepalive deadline that only moved later is noted on
  the armed entry, which re-arms itself when it comes due, and a
  cancelled timer is dropped when its entry fires. Through a Trojan TUN
  on the mobile profile, CPU per GiB fell 0.5% uploading and 0.7%
  downloading.
- **A read or write through the TUN stack no longer reschedules its own
  task:** after sending a command to the stack, a connection waited for
  the reply by waking itself, which cost a reschedule per read and, with
  two workers, often a wakeup of the other one. It now waits on the
  reply. Through a Trojan TUN on the mobile profile, context switches
  fell 10% and CPU per GiB uploading 1.1%; downloading was unchanged.
- **With worker threads, the TUN stack runs on them:** the instance's
  root tasks, the TUN's among them, ran on the thread that started it,
  outside the workers, and each time the stack woke a connection's task
  it woke a worker thread too. Through a Trojan TUN on the mobile
  profile's two workers, futex calls fell from about 32 000 a GiB to
  1 400 and context switches by 70%; downloads ran 7.3% faster at 2.3%
  less CPU a GiB, uploads 1.5% faster at the same CPU. On one thread
  nothing changes.
- **A packet from the TUN is no longer copied a second time:** the stack
  copied each packet the platform handed it into a zeroed buffer of its
  own; it now keeps the packet as it came and charges its bytes to the
  budget. Through a Trojan TUN on the mobile profile's two workers,
  uploads ran 1.8% faster at 1.6% less CPU a GiB, and on one thread
  1.3% faster at 1.3% less; downloading was unchanged.
- **A TLS write no longer copies bytes the socket has already sent:**
  when a write found the outgoing buffer full after a partial send, it
  grew the buffer, carrying the sent part along; it now drops the sent
  part first. Through a Trojan TUN on the mobile profile's two workers,
  uploads used 1.0% less CPU a GiB; on one thread nothing changed.
- **The TUN stack hashes a TCP flow's addresses once:** a segment looks
  up its flow about ten times, and each lookup hashed both socket
  addresses; the flow's key now carries its hash. Through a Trojan TUN
  on the mobile profile, CPU per GiB uploading fell 0.5% on two workers
  and 0.9% on one thread, about the size of the noise.

### Fixed

- **On a 32-bit router (mipsel, armv7), the stack's memory pressure now
  rises as its byte pools fill:** it multiplied a pool's bytes by 1000
  in the target's 32-bit word, which saturated past 4.29 MB, so the
  router profile's 16 MiB budget never left `Normal`. New connections
  were then refused only when a pool ran out, not at 85% as elsewhere,
  and caches were not reclaimed. The levels are now counted in 64 bits.
- **An idle TUN no longer wakes the device a hundred times a second:**
  the netstack ran its timers on a fixed 10 ms tick, traffic or not. It
  now sleeps until the next thing due (a retransmission, a delayed ACK,
  a keepalive, an idle UDP flow's or a TIME-WAIT's end), and not at all
  when nothing is. A mobile-profile TUN with no traffic, or holding 20
  idle connections, woke 0.6 times a second on one thread and 1.1 on
  two workers, against 112 and 313 before. Throughput and CPU per GiB
  through a Trojan TUN were unchanged. A connection whose reader has
  stopped, as an app's in the background, keeps it asleep too: a write
  waiting for the peer's window wakes on the window update, not on a
  10 ms retry.
- **Hysteria2 and TUIC clients recover from a server restart in about a
  second, not at the idle timeout:** a restarted server has lost the
  connection and cannot say so, and new streams went into it for 15 s.
  Once the server has sent nothing for a second (or four round trips)
  after a new stream, the next stream dials anew; what is still open on
  the old connection stays on it. Against a restarted sing-box server
  the first new stream worked after 1.04 s, against 15.1 s before. As
  an outage looks the same, the first stream after one can take up to
  a second longer (at most 1.1 s, against 0.4 s before).
- **TUIC downloads on long round trips are no longer held to quinn's
  default 1.25 MB a stream:** TUIC takes Hysteria2's windows by profile.
  Four streams against a sing-box server ran at 332 Mbit/s at 150 ms and
  479 at 300 ms, against 165 and 97 before and 233 and 146 for a
  sing-box client (preliminary). The runtime options for the windows
  are now `quic.receive_window`, `quic.stream_window` and
  `quic.send_window`, and apply to both (Breaking changes, above).
- **Hysteria2 and TUIC windows grow with the link, within the device's
  memory:** a stream's and a connection's receive windows start small
  and double when the application reads more than half of one within
  a few round trips, and the send window follows the congestion
  window. A shared budget for the process bounds what connections and
  send windows grow to. `quic.receive_window`, `quic.stream_window` and
  `quic.send_window` are now the starting sizes, and the new
  `quic.stream_window_max`, `quic.receive_window_max`,
  `quic.send_window_max` and `quic.window_budget` set the bounds (16, 64
  and 32 MiB with a 256 MiB budget on the desktop profile, 1 GiB on the
  server one).
- **The window budget follows the memory:** at start it is at most a
  quarter of the memory the system or the process's cgroup gives (a
  router's budget is that quarter, up to 64 MiB). While running, windows
  stop growing when less than `quic.free_memory_floor` is free (the
  system's MemAvailable, or a cgroup's limit less its use; 16 MiB on the
  router profile, 64 MiB on mobile and 128 MiB elsewhere), and on the
  mobile profile when the process holds more than `quic.anon_memory_max`
  (40 MiB) of anonymous memory. Windows that grew keep what they have.
  Linux and Android only. With four streams cold at 150 and 300 ms or 2%
  loss against a sing-box server (preliminary):
  - mobile (8, 32 and 16 MiB, 24 MiB budget): downloads at 1.17-1.67
    times a sing-box client's, at most 48.3 MB of anonymous memory;
    uploads at 1.04-1.44 (TUIC at 150 ms over 8 rounds).
  - router (4, 16 and 12 MiB): downloads at 0.93-1.18 times a sing-box
    client's in a 64 MiB cgroup, where sail peaked at 47.4 MiB and a
    sing-box client at 44-88 MB; uploads at 0.86-1.24 (Hysteria2 at 300
    ms held by the 12 MiB send window). With 16 MiB taken by another
    process in the same cgroup, nothing was killed.
- **QUIC's BBR measures the delivery rate (Hysteria2, TUIC, QUIC
  transports):** each ACK gives one sample from the newest packet it
  acknowledges, as quiche and Linux take it, where it was the bytes
  acked between two ACKs. The congestion window is at least 2 ms of
  the estimated bandwidth, and the send window holds up to what the
  peer lets be outstanding, as far as that is 20 ms of sending. With a
  32 MiB send window, uploads to a sing-box server at 150 and 300 ms or
  2% loss ran at 1.07-1.23 times a sing-box client's, from 0.85-1.16;
  sail to sail at 1.19-2.5 times sing-box to sing-box (preliminary). A
  server's 1000 connections at 2% loss or
  behind a deep queue held at most half of the 1 GiB window budget,
  which they had filled behind the deep queue.
- **The router profile bounds what a LAN client's TCP connection queues
  for it:** the new `inbound.tcp_receive_buffer` (KiB, 0 for the
  system's tuning) sets the receive buffer of accepted TCP connections;
  the router profile sets 1 MiB. Uploads through Hysteria2 or TUIC had
  queued 18-22 MB in four LAN connections, now 8. A client 8 ms away
  uploaded at 2706 and 2199 Mbit/s against 2631 and 2071 with the
  system's tuning.
- **QUIC and TLS take their upstreams' latest fixes** (quinn's `0.11.x`
  line past quinn-proto 0.11.19, and btls's `main`, merged into sail's
  forks):
  - QUIC (Hysteria2, TUIC, QUIC transports): no handshake starts once a
    QUIC endpoint's driver is gone, an illegal ordered read keeps the
    stream's receive state, switching a stream to unordered drops what
    was already read, a disabled idle timeout holds for accepted
    connections, accepting no longer holds the endpoint lock while TLS
    is set up, and ignored receive errors count towards the receive
    budget.
  - TLS: the `record_size_limit` the Firefox fingerprint offers is
    negotiated as RFC 8449 has it in more cases (0-RTT, and the alerts
    for a record over the limit), and BoringSSL skips clearing an empty
    error queue on every read and write.
  - Throughput and CPU per GiB through Trojan, REALITY and Hysteria2
    on loopback were unchanged.
