title: 架构
description: Sail 如何分离配置、路由、端点工厂、传输层与用户态网络栈。

Sail 围绕可复用核心组织，而不是一个只面向客户端的程序。客户端、服务端和中继共享配置模型、路由器、协议与传输层，变化的只是宿主和启用的端点。

## 请求路径

```text
宿主 / 操作系统
      ↓
入站监听 → 会话元数据 → 路由器 → 出站处理器
                                  ↓
                          传输层与 TLS
                                  ↓
                              网络套接字
```

入站创建包含来源、目标、网络类型、入站标签和认证用户的会话。可选嗅探或 DNS 解析补充元数据；路由器选择出站标签，出站管理器调用已经构建好的处理器图。

## Workspace

| Crate | 职责 |
| --- | --- |
| `sail` | 核心运行时、协议、传输层、DNS、路由与平台 trait |
| `sail-cli` | 命令行宿主与运行时参数 |
| `sail-ffi` | C 兼容生命周期与平台边界 |
| `sail-netstack` | TUN 的用户态 TCP/IP 数据面 |

## 配置与端点图

```text
JSON 或 .conf → 归一化模型 → 结构验证
                            → 端点依赖图
                            → 处理器与监听器
```

JSON 直接映射到 `config::model`，旧 `.conf` 先转换为同一模型。协议通过名称注册工厂；feature 决定构建中有哪些协议；工厂在创建前声明依赖与支持的通用模块。

Selector、Fallback、负载均衡和 MPTP 等复合出站依赖其他标签。Sail 对依赖图进行拓扑排序，在服务流量前报告缺失引用或环。

## 传输层组合

对流式代理，概念顺序如下：

```text
代理协议 → 复用/传输层 → TLS 或 REALITY → detour/拨号器 → 套接字
```

Hysteria2、TUIC 等 QUIC 原生协议拥有自己的连接方式，因此接受的模块不同。路由器只认识出站标签；健康检查、成员选择和多路径调度留在出站处理器中。

## TUN 与资源模型

TUN 入站把 IP 包送入 `sail-netstack`。网络栈管理 TCP 状态、UDP、分片、内存预算和调度，接受的流重新进入与套接字入站相同的会话与路由流程。

运行时配置档为 mobile、desktop、server、router 提供一致的资源预算，不改变可移植代理配置。监听器、健康检查、选择器和会话属于实例，在重载或关闭时通过显式句柄释放。
